## Project overview

`claude-plugin-vibe` is a **Claude Code plugin**: it is not an application with its own runtime, but a set of Markdown definitions (skills and agents) that support the "vibe coding" methodology — the human stays Product Owner (describes the need and evaluates the result), Claude writes, tests, reviews and delivers the code of the *other* projects on which this plugin is installed.

**Stack:** none — no language manifest (`package.json`, `pyproject.toml`, etc.). The content is Markdown (skills, agents) + one Bash script (`scripts/subagent-statusline.sh`) + JSON manifests (`plugin.json`, `marketplace.json`, `settings.json`).
**Type:** Claude Code plugin (meta-tooling), not an executable application.

## Architecture

## Development workflow (Vibe Coding)

The user stays **Product Owner only**: they describe what they want (new skill, new agent, README change) and evaluate the result — they do not write or manually test the files.

### Specifics of this repo

This repo has **no automated test suite and no linter**, by deliberate choice: there is no application code to run, only Markdown/JSON definitions consumed by Claude Code itself. Quality therefore rests on:
- manual review of the generated content (skills, agents, README) presented to the user before validation,
- strict consistency of frontmatter and structure between similar files,
- a basic JSON validation of the manifests before committing.

Do not introduce a `package.json`, a test suite or a linter for this repo without an explicit request from the user.

### Definition of Done

A task (new skill, new agent, documentation change) is done only if:

- [ ] The Markdown file(s) modified/created have a complete, valid frontmatter (`name`, `description`, and `argument-hint` or `context`/`agent` depending on the type; for an agent, `model:` and a bumped `version:` if its prompt or its `model:` changed — see existing models in `skills/*/SKILL.md` and `agents/*.md`)
- [ ] The JSON files touched (`plugin.json`, `marketplace.json`, `settings.json`) remain syntactically valid (manual check, e.g. `jq .` or careful reading)
- [ ] No hard-coded secret or credential
- [ ] `README.md` stays consistent with the existing skills ("Skills (commands)" table up to date) — use `/vibe:docs` if the change is user-facing
- [ ] No demo content or draft left in the delivered files
- [ ] The result is presented to the user for review before being considered done — there is no automatic gate here

**Never present a result as done without having reviewed it yourself** (there are no tests to guarantee it instead).

### Workflow for adding/modifying a skill or an agent

1. Find the existing skill/agent closest in scope and follow its structure (frontmatter, tone, level of detail)
2. Write/modify the Markdown file with a complete frontmatter
3. If JSON files are touched, carefully reread their syntax
4. Update `README.md` (skills table, managed sections) if the change alters what a plugin user sees — via `/vibe:docs`
5. Present the diff to the user for validation

### Self-correction loop

Without automated tests/lint, self-correction is limited to:
- rereading your own change before presenting it,
- checking consistency with similar existing files,
- flagging to the user any ambiguity about the scope of a new skill/agent instead of guessing.

## Testing conventions

No automated test suite in this repo (deliberate choice, see "Specifics of this repo" above). Confidence comes from human review of the produced Markdown/JSON content, not from executable tests.

## Evolution history <!-- keep -->

`evals/history/` charts how a skill or an agent evolved: `collect.sh <skill|agent> <case> [--dry-run] [--refresh] [--max N]` replays the **current** eval case on each past state (git worktree of the commit, with the working tree's `evals/` copied over it) and stores score, reliability (share of runs at 100%) and cost in `timeline.json`. The data is also embedded in `index.html` (between `/*DATA*/` and `/*END*/`), which plots score and cost per chart. One point = one distinct state (`version:` + `model:`), at the latest commit of that state: skills got `version` and `model` on 2026-09-29, so their curve only starts then. Each point keeps the case fingerprint; if the case changes afterwards, the point is marked outdated (`--refresh` measures it again). A case that grants `Bash` runs in Docker (image `vibe-eval`) on the worktree and needs `CLAUDE_CODE_OAUTH_TOKEN` (see `evals/docker/README.md`). The project skill `.claude/skills/eval-history/` is the entry point. Changing `version:`/`model:` of a skill or agent is what creates a new point: bump `version:` together with it.

## Agent model evals <!-- keep -->

Each agent in `agents/*.md` carries a `model:` field and a `version:` field (semver, e.g. `1.0.0`) in its frontmatter. The model is a cost/quality choice per agent, distinct from the manual review above; the version identifies unambiguously *which definition* of the agent produced a given score — both are validated with `claude plugin eval`, not with the test suite (which does not exist and must not exist here).

- Cases live in `evals/<case-name>/` (`prompt.md` for the prompt, `graders/*.md` for the criteria) — one case per scenario to check for an agent. Everything that defines a case is committed normally.
- A static fixture (a code file for the agent to review) needs **both**: `context.add_dirs` in `case.yaml` only declares a read permission, it copies nothing — you also need a `context.scaffold_script` (a bash script in the case folder, e.g. `fixture.sh`) that copies `fixtures/` into the run's empty workspace (`cp -r "$(dirname "${BASH_SOURCE[0]}")/fixtures" .`), run only via `--scaffold`.
- **`add_dirs` only names the case's fixture folders**: `add_dirs: [.]` is refused by the CLI ("an add_dir may only name fixture directories inside this case") and every run fails at $0 — write `add_dirs: [fixtures]`. Several skill cases still carry `[.]`: fix it first when evaluating their target (seen on changelog on 2026-09-24, then on auto on 2026-09-26).
- Any change to an agent's prompt or `model:` bumps its `version:` (patch for a wording adjustment, minor for a checklist/category change, major for a scope overhaul) — it is this bump that signals a new eval run is due, not a manual inspection of the diff.
- `evals/results/` is regenerated on every run and gitignored (`report.html`, `aggregate-result.json`, costs tied to the moment of the run) — except `evals/results/history.md`, which stays tracked: after a run judged significant (a `version:` bump on an agent, or a new case), add a row to it (date, agent, agent version, case, model, score, pass rate, cost, tokens, short note) before committing. The cost comes directly from the CLI total; tokens need `--keep-temp` (see history.md for details) — no extra API cost, just a run that must not be cleaned up. An identical score between two runs does not make them equivalent: the one that uses fewer tokens/$ is the better one.
- **Changing a case outdates its own history.** Touching a fixture, adding/splitting/removing a grader or changing a weight changes *what* the score measures: the rows already written for that case are no longer comparable to the following ones. In the same commit as the case change, mark each of those rows with a ⚠️ in the `Case` column and open their note with `**Obsolete (YYYY-MM-DD):** <what changed in the case>` — never delete the row, never touch its figures. The comparison restarts from the first run after the change.
- **A fixture never names the defect it contains.** A fixture's comments describe where the code is called from and what it is for ("Called from the checkout flow", "Called once per frame; the frame budget is 16ms"), never what is wrong. A comment like `# Isolation: shared mutable state between tests` turns the case into a copying exercise and the score into a 1.00 that guarantees nothing. Same rule on the precision side: clean code does not need to defend itself — no "not feature envy", no "no shared mutable state". The only exception is a justification that *is part of the evaluated domain* and that the agent's definition tells it to accept (an explicitly marked fire-and-forget, a cache with a measured cost): there, the comment is the signal, not the answer.
- **One grader = one verifiable claim.** A precision case is split into one grader per neutralized pattern, not one catch-all grader: a single LLM judge carrying two thirds of the score makes the case binary and noisy (see the 0.56 / 1.00 / 0.33 of `review-naming` on an unchanged fixture). On the recall side, one grader per category, each with **its own anchor in the code** — if three graders point at the same line under three labels, you measure the verbosity of the report, not the detection.
- **The prompt injected into an agent reproduces word for word what the skill really sends it** (contract of `skills/review/SKILL.md`, exclusion list, dynamic-verification flag). An eval that simplifies the contract tests an agent that does not exist — and may contradict its own graders.
- **A case's `allowed_tools` must cover the `tools:` the agent needs *in the tested mode*.** `review-tests`, `review-dependencies` and `review-web-security` declare `Bash`: without `--allow-tools Bash` the case measures an amputated agent. The only exception is `review-web-security` in static mode: its prompt forbids running anything, so its two static cases have no `Bash` — the dynamic-verification case is the one that grants it. What the sandbox provides also matters — no `pytest` installed, so test fixtures run with `python3 -m unittest`.
- **A case that grants `Bash` runs in Docker, not on the host**: on the maintainer's Mac, `~/.docker` contains symbolic links (Docker Desktop) and the eval sandbox refuses every `Bash` case (`DOCKER_CONFIG` changes nothing). `evals/docker/run.sh <case-glob> [flags]` runs the case in a Linux container with the canonical flags, then `tokens.py` on the same run — see `evals/docker/README.md`. `CLAUDE_CODE_OAUTH_TOKEN` (or `ANTHROPIC_API_KEY`) must be in the environment; if it is missing, report it rather than removing `Bash` from a case to run it on the host. Cases without `Bash` still run on the host.
- **`--allow-tools` only takes gated tools** (`Bash`, `Write`, `Edit`, `WebFetch`, `mcp__*`), space-separated (`--allow-tools Bash Write`), not the case's `allowed_tools` joined with commas: `Read`/`Grep`/`Glob`/`Agent` come from `case.yaml`.
- **A case's `timeout_seconds` must fit the agent's `effort:`.** At 300 s, `review-tests` on sonnet `effort: max` timed out on 2 of 3 runs (seen 2026-09-28): a timed-out run scores ~0.1 on every grader, and `tokens.py` then stops with "no `result` line … Interrupted run?", so the whole run gives no token figure. A score collapse together with `timed out after 300s` in the eval table is a timeout, not a regression — raise the case to 600 s (like the heavier cases) before reading anything into it.
- **The eval sandbox has no network.** A tool that queries a registry (`npm audit`, `pip-audit`…) fails ("denied access to registry.npmjs.org", seen on `review-dependencies` on 2026-09-25) or, with `--offline`, returns "0 vulnerabilities" without checking anything. A case that depends on an audit therefore measures how the agent handles an audit that could not run, never the tool's real output.
- **Reading a Docker run's output**: the `--keep-temp` dirs die with the container (`--rm`), but each run's last message stays in `evals/results/<timestamp>-<case>/aggregate-result.json`, in the `cases[0].arms.with[<run>].graders[<i>].evidence` field of the `llm` graders with `focus: last_message`. Graders only keep their votes there, not the judge's reasoning. An `llm` grader with `focus: { source: file, path: … }` keeps that whole file in its `evidence` too: that is how to read a generated file (a README, a `docs/` page) after a Docker run, e.g. to tell a wrong output from a grader aimed wrong.
- **A case must be able to reach 1.00.** Two mutually exclusive graders (path A / path B of the same skill) cap the score below the default `--threshold 1.0`: use a single grader that tolerates both paths and checks that the agent *announces* the one it took.
- **Grader pitfalls seen on the `feature-*` cases (2026-09-29).** (1) A `file_exists` grader on a file already present in the fixture (with or without `exists: true`) fails with "missing (expected present)" even though the file is there and the agent edited it; those on a file created by the run pass: use it only for a file the skill creates, and check a pre-existing file with an `llm` grader with `focus: { source: file, … }` or with a regex on its content (seen on `feature-implements-via-tdd-in-auto-mode`; the `fix-*` cases carry the same two `*-file-exists` graders to fix). (2) A `criteria` of an `llm` grader that copies code containing `${…}` (template literal) makes 3 votes out of 3 fail on a file that is nevertheless identical (`evidence` = the exact file): describe the expected content in words instead of copying it. (3) A `tool_order` whose `after` is a command already run at baseline (here `npm run build`) compares with the first occurrence and always fails (`Edit@34 does NOT precede Bash@11`): count occurrences with `tool_used` + `min: 2`. (4) An agent reads the small files of a fixture while exploring: a rule hidden in a readable build script will not fail the build, the agent anticipates it — a narrative grader must accept both paths.
- **Grader pitfalls seen on the `fix-*` case (2026-09-30).** (1) An `llm` grader on the final report cannot check the red step: `fix`'s report contract only asks for "the test that now covers the bug", so the agent often omits that the test failed first (3 FAIL votes while the trace shows the red `npm test` run). Grade red from the tool calls instead: `tool_order` test edit → source edit, plus `tool_used` on `Bash` `input_match: "npm test"` with `min: 3` (baseline, red, green). (2) `tool_used` with `min: 0` / `max: 0` works to forbid an edit (e.g. patching the caller instead of the shared helper).
- **Reading a Docker run's trace:** `evals/docker/run.sh` now copies each run's trace to `evals/results/<timestamp>-<glob>/traces/<case>-run<N>.jsonl` (the `tool_use` lines of `message.content` give the tool sequence, in the same order as the `Edit@N`/`Bash@N` indices of the `tool_order` graders) — without it the trace dies with the container.
- **A dynamic-verification case is proven by hand before being committed.** The fixture app has no dependency to install (standard library), listens on `127.0.0.1` and keeps its state in memory, so a local instance is disposable and restartable; each expected exploit is replayed with curl and its observed result is copied into the matching grader. A dynamic grader that describes an exploit never executed measures a belief, not the agent.
- **A scaffold writes nothing outside the run's workspace.** A `../origin.git` is shared between concurrent runs and survives cleanup; the fallback bare repo lives in the workspace (and in `.gitignore`).
- Running an eval costs real tokens (real calls to the agent(s) + an LLM judge over several runs) — it is a manual action of the Product Owner or of Claude on explicit request, never triggered automatically by a skill or a hook.
- Validate a **new or modified** case on its own with `--runs 1` before running it at full scale — a broken setup (fixture not exposed, wrong `subagent_type`, etc.) costs the same price on every failed run, and is discovered for the price of one. Once the cases are validated, grouping them in a single command (`--case "review-*"`) costs no less than one case at a time: each run is an independent process, nothing is shared between cases. Grouping only helps comfort (a single report); `-j`/`--concurrency` reduces waiting time, not the price; `--ablation none` divides the price by ~2 once you no longer compare to a baseline without the plugin.

## Constraints

- Never commit secrets or credentials
- Content of `skills/*/SKILL.md` (and neighbouring files such as `skills/feature/workflow.md`) and `agents/*.md` (instructions to Claude, user dialogue, report templates) always written in English, without exception — the plugin runs on projects/conversations in any language, no text frozen in a particular language belongs there
- Every skill (`skills/<name>/SKILL.md`) and every agent (`agents/<name>.md`) must have a complete frontmatter consistent with the existing files (`tools:` read-only on the review agents, except those that execute something)
- No maintainer-facing text ("kept identical", "update both together") in a runtime prompt: what is shared lives in a single file read at invocation (`skills/feature/workflow.md`, agent contract in `skills/review/SKILL.md`), see ADR 004
- Do not leave an orphan skill/agent file or obsolete content after a rename/deletion
- Keep the README as an up-to-date index of the skills and of `docs/` (see `/vibe:docs`)
- Do not add an application stack (Node, Python, etc.) to this repo without an explicit request — this is not that kind of project
  - Exception: `evals/` contains everything the evaluations need and can therefore host scripts (Python, Bash…) — fixtures, scaffolds, tools like `evals/tokens.py`. They do not constitute an application stack of the plugin.
