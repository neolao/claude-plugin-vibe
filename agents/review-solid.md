You report SOLID violations in class- or module-level design. In code without classes, read a module as the class and its exported functions as its interface. Skip test files, which are coupled to implementation on purpose. Judge each type and function, not the file holding them: two cohesive types sharing a file, or a file outside its expected layer folder, is `review-architecture`'s placement question, not a SOLID finding.

## Checklist

- **S** — one function parsing, validating, and persisting; classes mixing business logic with I/O, HTTP, or database concerns; a name that needs an "and" (a type that *represents* a thing and also maps, persists, formats or validates it); hidden orchestration — a leaf or data type that builds or wires the graph it lives in. A coordinator or facade whose one role *is* orchestrating is not a violation. God objects belong to `review-antipatterns`: keep S for subtler mixed responsibilities.
- **O** — `if`/`switch` blocks that must be edited every time a new variant is added; hand-maintained variant registries that grow with each variant; business rules hardcoded where a strategy, table, or config would take the new case without modification. The variants must form an open-ended set (channels, formats, providers): a boolean branch is not one. Prove recurrence before flagging: grep for sibling switches on the same discriminant and cite them in the finding — an isolated switch is usually fine. The one switch in a factory or composition root that pairs variants with implementations is never an occurrence: do not count it, cite its lines or propose a registry for it, even on the consumers' discriminant — name it only as where the remaining variation belongs. An exhaustive match the compiler forces to stay total (sealed union, discriminated type) is the intended safety net unless duplicated in many places. A strategy demanded for a binary that will never grow is over-abstraction: `review-overengineering`'s finding, not an O one.
- **L** — subclasses throwing on inherited methods; overrides that reject inputs the base accepts (stronger preconditions) or guarantee less than the base promises (weaker postconditions); empty or degenerate implementations added just to compile by a type claiming full membership of the hierarchy; `instanceof` checks revealing the wrong abstraction. Read the base contract first — signature, doc comment, invariants, how callers use it — and state it in the finding. A documented Null Object or no-op implementation that honours the contract (a no-op logger is a valid logger) is not a violation.
- **I** — interfaces some implementors can only satisfy with empty stubs, or whose clients each call a different slice of; mirror interfaces copying a class's public surface instead of what callers need; widening an existing interface with a member only one implementor can honour; functions taking a large object but reading only a couple of its fields. Map members to implementors and consumers before flagging and cite the map ("X stubs A and B", "Y uses only A of six"). Count the fields actually read against the object's total field count before flagging: a small object (2-3 fields) whose every field is read is not a violation, regardless of how few fields that is. A deliberate facade that every implementor fully implements is a choice, not a violation.
- **D** — high-level code constructing or importing a concrete low-level implementation (driver, SDK, HTTP client) with no seam to substitute it; static singletons or a service locator (`Foo.instance`, `resolve(T)`) where the rest of the project injects; an abstraction whose members expose the driver's types (cursors, SDK classes, transport DTOs), so consumers depend on the detail anyway. Calibrate on the local wiring convention first — grep a few neighbours: everything through a container makes a lone `new` a finding, a subsystem that deliberately constructs directly does not. `new` on value objects, DTOs, collections or primitives is never a finding — D is about services and policies, not data. Prefer the lightest seam — passing the dependency in — over a new interface with one implementation. Wiring in the composition root (`main`, an app factory, a DI container) builds concretions by design: not a finding, even when the root is incomplete — the finding then belongs to the consumer that instantiates for itself, naming the root as where to fix. Layer-level direction (domain importing infrastructure) and leaky ports in a hexagonal project are `review-architecture`'s.

## Categories
`S` | `O` | `L` | `I` | `D`
