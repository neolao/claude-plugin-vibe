# Development

How to work on the plugin itself. There is nothing to install or build: the deliverables are Markdown instruction files, one shell script, and three JSON manifests, all consumed directly by Claude Code.

## No tests, no linter — by design

This repo deliberately has no test suite, package manifest, or linter: there is no executable application code, only definitions interpreted by Claude Code. Quality relies on:

- re-reading generated content before presenting it,
- strict structural consistency with neighboring files (same frontmatter, tone, level of detail),
- syntactic validation of touched JSON manifests (`jq . .claude-plugin/plugin.json`, etc.).

Do not introduce a `package.json`, test framework, or linter without an explicit request.

## Adding or changing a skill

1. Find the closest existing skill in `skills/*/SKILL.md` and mirror its structure.
2. A skill lives in `skills/<name>/SKILL.md` with frontmatter:
   - `name` — slug matching the directory, invoked as `/vibe:<name>`
   - `description` — one line, shown in skill listings
   - `argument-hint` — optional placeholder for `$ARGUMENTS`
   - `user-invocable` — optional, default `true`; set `false` for an internal skill hidden from the `/` menu and callable only by other skills via the Skill tool (see `skills/tasks/SKILL.md`)
3. If the change is user-visible, update `README.md` (the "Skills (commands)" table is hand-written; the Features/Install/Usage/Documentation sections between `vibe:begin:*`/`vibe:end:*` markers are regenerated by `/vibe:docs` — never edit inside markers by hand).
4. Record the change in `CHANGELOG.md` under `[Unreleased]` (Keep a Changelog format, end-user voice).

## Adding or changing a review agent

Same approach: one file `agents/review-<dimension>.md` with frontmatter `name` + `description` + `tools` (read-only — `Read, Grep, Glob` — unless the agent genuinely executes something), auditing exactly **one** quality dimension. The body holds only the scope sentence, the checklist, and the `## Categories` enum: the finding format, severity scale, and read-only rule live once in `skills/review/SKILL.md` and are injected into every agent prompt. If a check borders an existing agent's territory, say so in one sentence in the scope — every check has a single owning agent. Conditionally-relevant agents (`review-ddd`, `review-web-security`) state their activation condition in the description.

## Adding or changing an expert agent

One file `agents/expert-<domain>.md`, frontmatter `name` + `description` (the description states the trigger — "Consult when the task…" — since it drives per-task selection). Body: one scope sentence (including the out-of-scope routing to a sibling expert) plus a short domain checklist of non-obvious requirements. The consultation formats (plan consultation returns `REQUIREMENTS`/`RISKS`/`TEST SCENARIOS` plus an optional `OPEN QUESTIONS` list, implementation consultation answers one question) are stated once in `skills/feature/workflow.md`, which the invoking skills pass in the prompt. Before adding a new domain, check it doesn't already have a `review-*` counterpart — the roster is deliberately scoped to avoid that overlap (`.vibe/decisions/001-expert-personas-scope.md`). A domain with a review counterpart still gets an expert only as a documented, narrow exception (see `.vibe/decisions/003-realtime-rendering-expert-exception.md` for the precedent) — never silently. Keep each file terse: it is loaded into context on every consultation.

## Conventions that must hold

- No secrets or credentials in any file.
- `skills/*/SKILL.md` (and companion files such as `skills/feature/workflow.md`) and `agents/*.md` content — instructions to Claude, user-facing dialogue, report templates — is always written in English, no exceptions: the plugin runs on projects and conversations in any language, so nothing in its own source should be pinned to one. `skills/clarify/SKILL.md` is the one deliberate case where the *live dialogue* still adapts to the conversation's language at runtime — its own instructions authoring it are English like everything else, only the behavior they describe is dynamic.
- No orphan skill/agent files after a rename or removal.
- JSON manifests (`plugin.json`, `marketplace.json`, `settings.json`) stay syntactically valid.
- The `.vibe/` map of this repo is dogfooding — regenerate it with `/vibe:sync` rather than editing it by hand (entry lifecycles are listed in `.vibe/README.md`).
- Generated `.vibe/` content and every skill's end-of-run report use short, plain sentences — no filler, one fact per line (`.vibe/decisions/002-concise-writing-convention.md`).

## Releasing

Run `/vibe:release patch|minor|major` (or an explicit version): it finalizes the changelog, refreshes the docs, bumps `version` in `.claude-plugin/plugin.json`, commits and tags. Install locally for testing via `/plugin marketplace add neolao/claude-plugin-vibe` + `/plugin install vibe`.
