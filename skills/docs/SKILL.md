# /vibe:docs — Project Documentation Maintainer

Generate or refresh two kinds of documentation, both derived from the real project state (manifest, CHANGELOG, `.vibe/`, code) — never invented:
- **README managed sections**, written **for the end user**: no file, function, or module names. Nothing outside the managed markers is ever touched — not a character, not whitespace.
- **`docs/` files**, written **for developers** who need to understand the project: real module names, paths, and commands are welcome as long as they come from the code.

Both in short, plain sentences — a fact per line beats a dense paragraph.

## Step 1 — Read the sources

`README.md` (managed sections and the hand-written content around them); the manifest(s) (name, description, install/run/test scripts); `CHANGELOG.md`; `.vibe/index.md`, `modules/`, `glossary.md`; `.env.example`; `CLAUDE.md`; the code itself (tree, entry points, main modules — `.vibe/` is not the only source); every file currently in `docs/`. `--full` in `$ARGUMENTS` forces full regeneration of `docs/`.

Invoke the `vibe:tasks` skill with `Update README sections` → `Update docs/`.

## Step 2 — README managed sections

Only the content between a marker pair is rewritten:

```markdown
<!-- vibe:begin:features -->
...generated content...
<!-- vibe:end:features -->
```

| Section | Markers | Derived from |
|---|---|---|
| Features | `vibe:begin:features` / `vibe:end:features` | `CHANGELOG.md`, all versions + `[Unreleased]` — deduplicated, phrased as benefits, not a changelog copy |
| Installation | `vibe:begin:install` / `vibe:end:install` | manifest — prerequisites, the install command, how to verify it, update/uninstall when the method provides them |
| Usage | `vibe:begin:usage` / `vibe:end:usage` | manifest scripts and real entry points — every user-facing command with realistic examples checked against the code |
| Documentation | `vibe:begin:docs-index` / `vibe:end:docs-index` | every Markdown file in `docs/`, filled in Step 3 once `docs/` is final |

- README with managed sections → rewrite inside each pair.
- README without managed sections → never insert them silently into a hand-written file: list the sections that could be managed and ask which to add (end of file by default).
- No README → create it: title, one-paragraph description (manifest + `CLAUDE.md`), the four managed sections.

## Step 3 — docs/

`docs/` Markdown files are fully generated and start with:

```markdown
> Generated by /vibe:docs — manual edits will be overwritten; use README for hand-written content.
```

**Inventory the aspects** a new developer must understand, from the Step 1 sources including the code walk, and create one file per aspect — only when the condition holds and there is real substance:

| File | Aspect | Only if |
|---|---|---|
| `docs/architecture.md` | main modules, responsibilities, data flow | ≥ 2 identifiable modules |
| `docs/configuration.md` | env vars and options: name, purpose, default, required | the project has configuration |
| `docs/data-model.md` | entities, relationships, persistence | a schema, models, or migrations exist |
| `docs/api.md` | HTTP endpoints or a library's public surface: inputs, outputs, errors | an API or public surface exists |
| `docs/workflows.md` | business flows, lifecycles, state machines | multi-step processes exist |
| `docs/testing.md` | kinds of tests, what each covers, how to run them | a test suite exists |
| `docs/development.md` | local setup, build, project conventions | setup takes more than one obvious command |
| `docs/<aspect>.md` | any other substantial aspect (`caching.md`, `auth-flow.md`), name kept stable across runs | it would confuse a new developer otherwise |

Guardrails: never an empty or near-empty file; never a paraphrase of `.vibe/` or the README — each doc gives a reading those sources do not; a generated file whose aspect disappeared from the code is deleted and reported; a `docs/` file without the banner is hand-written — leave it alone and mention it.

**Diagrams**: when one explains better than prose, embed a ` ```mermaid ` block (`graph`/`flowchart` for architecture, `sequenceDiagram` for flows, `erDiagram` for data, `stateDiagram-v2` for lifecycles) — derived from the code, ~15 nodes max, always paired with explanatory text.

**Incremental by default**: regenerate a file only when its sources changed; `--full` regenerates every applicable file.

**Non-Markdown files in `docs/`** (`.html`, `.css`, `.js`, images, `.nojekyll`, …) are never modified and never indexed.

**Documentation index**: once `docs/` is final, rewrite the `docs-index` section so it lists every Markdown file in `docs/` — generated or hand-written — one line each (relative link + one user-facing sentence), sorted by path, entries for vanished files removed; "No additional documentation yet." if `docs/` is empty.

## Step 4 — Report

Short, plain sentences: README sections updated / unchanged / absent; each aspect considered, marked created / updated / unchanged / skipped / deleted with its reason; any hand-written `docs/` file left alone. Do not print file contents unless asked. Do not commit — the caller or the user does.
