# /vibe:sync — Codebase Map Sync

Maintain `.vibe/`, the structured context map that lets Claude understand the codebase quickly in any session. **Full mode** when `.vibe/index.md` is absent or `--full` is given; **incremental mode** otherwise — only what changed since the last sync is re-derived.

## Step 1 — Scope

Read `CLAUDE.md` for the source directories and stack.

Incremental mode: take the date from `index.md`'s first line (`> Generated by /vibe:sync on YYYY-MM-DD`) and collect the changed files from **both** `git log --since="<date>" --name-only --pretty=format: -- <source_dirs>` and `git status --porcelain -- <source_dirs>` — `/vibe:feature` and `/vibe:fix` invoke sync before committing, so uncommitted changes count. Nothing changed → report "already up to date" and stop. Otherwise only the functional zones touched by those files are updated.

Source files exclude tests (`*.test.*`, `*.spec.*`, `test_*.py`, `tests/`, `__tests__/`), dependencies (`node_modules/`, `vendor/`, `.venv/`), build output (`dist/`, `build/`, `out/`, `target/`), generated files, configuration (`*.config.*`, `*.json` without logic), and migrations.

## Step 2 — `.vibe/modules/<name>.md`

Functional zones follow the directory structure (`src/auth/`, `src/api/`, …); a flat project is grouped by responsibility. One file per zone:

```markdown
# Module: [name]
**Role:** [one sentence]
**Files:** `src/auth/index.ts`, `src/auth/middleware.ts`
**Exports:** `signIn(email, password): Promise<Session>`, `AuthMiddleware`
**Depends on:** `modules/db.md`, `modules/config.md`
```

## Step 3 — `.vibe/models.md`

Key types, interfaces, schemas, and data structures (incremental: only those whose source changed):

```markdown
# Data models

## [ModelName]
| Field | Type | Notes |
|---|---|---|
| id | string | UUID |
Defined in: `src/types/user.ts`
```

## Step 4 — `.vibe/glossary.md`

A glossary term is a **business concept the project owns and names** — what the domain does, not how the code does it. Test: would a domain expert who does not know this codebase recognize the term? Not terms: third-party library or API names, DOM/protocol/infrastructure vocabulary, error class names (the failure belongs in the relevant concept's definition), implementation patterns ("buffer-cache pattern"), internal plumbing (synthetic cache keys), configuration keys and values.

```markdown
# Ubiquitous Language

## [Domain term]
[1–3 short, plain sentences from how the code actually uses the concept: what it is, its responsibility, its relations to other terms — never a stub]
**Do not confuse with:** [similar but distinct term, if any]
_Sources: `src/orders/checkout.ts`, `src/orders/cart.ts`_
```

The glossary is fully generated and self-cleaning — no confirmation, no definition left for a human to refine; every entry is traceable through its `Sources:` line. Each sync: **adds** newly detected concepts; **redefines** an entry only when the code backing it changed; **removes** entries that violate the criteria above or whose sources no longer exist with no new usage found (one-line reason each). Incremental mode re-derives only entries with a source in the changed set but still checks every `Sources:` line for existence. A legacy entry without `Sources:` keeps its text and gains the line if it is non-empty, not a stub, and consistent with the code; otherwise it is replaced.

## Step 5 — `.vibe/index.md`

Imported into every session via `@.vibe/index.md` in `CLAUDE.md`, so its cost is paid at every session start: one line per module, a short list of observed patterns (found in the code, not declared in `CLAUDE.md`), one short plain sentence per bullet, no detail — details live in the files below.

```markdown
# [PROJECT_NAME] — Codebase index
> Generated by /vibe:sync on YYYY-MM-DD. Re-run to update.

## Modules
- [`modules/auth.md`](modules/auth.md) — [one line]

## Observed patterns
- [one fact per bullet]

## Other context files
- [`models.md`](models.md) — data models
- [`glossary.md`](glossary.md) — ubiquitous language
- [`decisions/`](decisions/) — architectural decision records (if present; maintained by /vibe:feature)
- [`escalations.md`](escalations.md) — recorded escalation diagnoses (if present)
```

## Step 6 — `.vibe/README.md`

Written in full mode, and in incremental mode when absent or no longer matching this template (the plugin may have changed it):

```markdown
# .vibe/ — Project context

Maintained by the `/vibe:*` commands. Lifecycle of each entry:

| Entry | Lifecycle |
|---|---|
| `README.md`, `index.md`, `modules/`, `models.md` | ♻ Regenerable — recreated by `/vibe:sync`, do not edit by hand |
| `glossary.md` | ♻ Regenerable — fully derived from code, auto-cleaned by each sync, do not edit by hand |
| `decisions/` | 🔒 ADRs — append-only, never regenerated, do not delete |
| `backlog/` | 🔒 Work data — never regenerated, do not delete |
| `escalations.md` | 🔒 Work data — append-only escalation log, do not delete |
| `last-review.md` | ♻ State marker — rewritten by each `/vibe:review` run |
| `auto-state.md` | 🔒 Work data — `/vibe:auto` run state + append-only journal; deleting it loses the ability to resume an interrupted run |

Never delete the whole `.vibe/` directory: only the ♻ entries can be recovered by re-running `/vibe:sync`.
```

A legacy single-file `.vibe/decisions.md`: propose (explicit confirmation) to split each `## [YYYY-MM-DD] Title` section into `decisions/NNN-slug.md` (chronological numbering, `status: accepted`) and delete the file; if declined, leave it and add a `decisions.md` row marked `🔒 Legacy — superseded by decisions/`.

## Step 7 — Report

Short, plain sentences: mode; modules updated out of total; data models updated; glossary terms (added, redefined, removed with reasons). Do not print file contents unless asked.
