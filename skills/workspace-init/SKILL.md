# /vibe:workspace-init — Multi-Repo Workspace Bootstrap

A **workspace** is a parent folder — never itself a Git repo — holding several sibling repos. This skill sets up, or idempotently refreshes, two things:
- the **hub repo**: a Git repo with no application code that plans across the others — `repos.md` (registry of siblings) plus a workspace-scoped `.vibe/backlog/` and `.vibe/decisions/`. Recognized by a structural **marker**, never a fixed name: a directory with `.git/` and `repos.md` at its root;
- the **workspace-root `CLAUDE.md`**: a local, never-committed file at the parent folder's root pointing to the hub and listing the siblings.

Re-run whenever a repo is added, retired, or renamed. This skill never pushes.

## Step 1 — Where are we?

- cwd has the marker → inside the hub repo: the workspace root is its parent; go to Step 3.
- cwd has `.git/` but no `repos.md` → a code repo: stop with "Run `/vibe:workspace-init` from the workspace root (the parent folder, not inside a repo), or from the hub repo itself."
- cwd has no `.git/` → the workspace root; go to Step 2.

## Step 2 — Locate or create the hub repo

Prefer the pointer: a workspace-root `CLAUDE.md` from a previous run names the hub directory on its `## Hub repo` line — valid if that directory still has the marker. Otherwise scan cwd's direct subdirectories for the marker.

Not found → first bootstrap. `AskUserQuestion` for the hub directory name (pre-fill `$ARGUMENTS`, else suggest a neutral name such as "roadmap") and an optional Git remote; `mkdir` + `git init` (+ `git remote add origin`), or `git init` in place if the directory exists without `.git/`. Then invoke the `vibe:clarify` skill with "the purpose of this new multi-repo workspace — why these repos belong together and what it's meant to achieve": `settled`/`partial` → its `### Synthesis` is the workspace vision used in Step 5; `abandoned` → no vision paragraph.

## Step 3 — Task list

Invoke the `vibe:tasks` skill with: `Update repos registry` → `Ensure .vibe/ scaffolding` → `Write hub repo CLAUDE.md` → `Refresh hub repo README` → `Refresh workspace CLAUDE.md`.

## Step 4 — `repos.md`

Scan the workspace root's direct subdirectories with `.git/`, excluding the hub. Already listed → keep `status` and `role` exactly as they are (never overwrite a human judgment). New sibling → `status: active` if it has `.vibe/backlog/`, otherwise `AskUserQuestion` for the status (`active` picked by `/vibe:next-task` / `planned` no code yet / `idea` no repo yet) and a one-line role — never guess the role. Listed but gone → report the discrepancy and ask before removing.

```markdown
# Repos registry

Maintained by /vibe:workspace-init — re-run after adding, retiring, or renaming a repo in the workspace.

| Repo | Status | Role | Remote |
|---|---|---|---|
| api | active | REST backend, owns the `orders` domain | git@github.com:acme/api.git |
| sdk | planned | Shared TS client — not started | — |

## Naming convention
[the workspace's repo-naming pattern, or "None documented yet."]
```

Then create `.vibe/backlog/` and `.vibe/decisions/` in the hub if absent, never touching existing items or ADRs.

## Step 5 — Hub repo `CLAUDE.md`

Written here, not by `vibe:init` (whose stack detection and DoD assume application code):

```markdown
# CLAUDE.md — [hub repo name] (workspace hub — no code)

> Auto-generated by /vibe:workspace-init. Edit freely — re-run /vibe:workspace-init to refresh the registry/scaffolding.
> Add `<!-- keep -->` on a section heading to preserve it on regeneration.

## Role

This repo holds no application code. It is the source of truth for cross-repo planning: [repos.md](repos.md) registers every sibling repo (status, role, remote); `.vibe/backlog/` and `.vibe/decisions/` hold Product Owner decisions and ADRs spanning more than one repo.

[Vision paragraph from Step 2, in the project's language — omitted on a refresh run.]

**Items here are never implementable work** — never picked up by `/vibe:feature`, `/vibe:fix`, or `/vibe:auto`. Run `/vibe:next-task` from the workspace root to pick and ship actual work in the right repo.

## Backlog & decisions

Same format as any vibe-managed repo, scoped to workspace-level concerns: which repo owns what, cross-repo sequencing, naming conventions. `/vibe:backlog` works here too. Managed by hand, never by an autonomous run.
```

Then invoke the `vibe:docs` skill (README skeleton or refresh) and the `vibe:sync` skill — a hub has little source; "nothing to update" is a normal outcome, noted in the report.

## Step 6 — Workspace-root `CLAUDE.md`

Full idempotent overwrite (with `<!-- keep -->` support), never committed — the folder is not a repo and the file regenerates from `repos.md`:

```markdown
# CLAUDE.md — [workspace name] (workspace root — not a git repo)

> Auto-generated by /vibe:workspace-init. This directory is not version-controlled: this file is local-only convenience context.
> Re-run /vibe:workspace-init here to refresh it. Add `<!-- keep -->` on a section heading to preserve it.

## Hub repo
`[hub-dir]/` — source of truth for cross-repo planning (`repos.md`, workspace-scope backlog/decisions in `.vibe/`). Its items are Product Owner decisions, never implementable work.

## Sibling repos
| Repo | Status | Role |
|---|---|---|
[mirrored from repos.md]

## Cross-repo workflow
Run `/vibe:next-task` from this directory to pick, implement, and ship the next eligible task across active repos.
```

The `## Hub repo` line is the pointer Step 2 and `/vibe:next-task` read — keep the exact directory name in the backticks.

## Step 7 — Commit and report

In the hub: if `repos.md`, `.vibe/`, `CLAUDE.md`, or `README.md` changed, one commit — `chore: bootstrap hub repo` on first init, `chore: refresh workspace registry` otherwise; nothing changed → say so. Report, short and plain: hub location (created / existed); repos added, updated, flagged missing; files refreshed; commit or "nothing to commit"; a reminder to push the hub when convenient.
